# CSL Helpdesk Client — клиент заявок для Windows (Jira h.csl.by)

Графическое приложение для сотрудников организации, которое:
- разворачивается **всем пользователям через групповые политики домена (GPO)**;
- использует **один общий логин/пароль организации** (вводится администратором один раз);
- при первом запуске один раз запрашивает **контактный телефон** (сохраняется и редактируется);
- **собирает сведения о ПК** (CPU, RAM, диски, материнская плата, BIOS, сеть) и ID **AnyDesk / RustDesk**;
- позволяет отметить **чекбоксы неисправностей**, приложить **скриншот** и **голосовой комментарий**;
- по кнопке «Отправить» формирует заявку и отправляет её на **h.csl.by** (Jira Server);
- **самообновляется из GitHub Releases** при выходе новой версии.

## Быстрый старт для администратора

1. Создайте сервисный аккаунт Jira (только право создавать заявки) — см. безопасность.
2. Соберите `CSLHelpdesk.exe` — он **создаётся автоматически** GitHub Actions при каждом
   пуше (готовый файл в **Releases** / артефактах Actions). Либо локально:
   `powershell -File deploy\build-exe.ps1`.
3. Заполните `deploy/admin-config.json.template` (Jira + `github_repo`) → `config.json`.
4. Положите `CSLHelpdesk.exe` и `config.json` на GPO-шару и назначьте
   `deploy/Install-HelpdeskClient.ps1` как **Logon**-скрипт.
5. У пользователей появляется ярлык; приложение готово к работе.

Подробно: **[DEPLOYMENT.md](DEPLOYMENT.md)** · для продолжения разработки: **[AGENTS.md](AGENTS.md)**.

## Варианты реализации (сравнение)

| Вариант | Итог |
|---|---|
| **Python + PyInstaller → EXE** ✅ | один файл EXE, минимум зависимостей, логику можно тестировать в CI; EXE ~15–30 МБ. Python нужен только для сборки |
| C# .NET WinForms/WPF | нативно для Windows, но сборка Windows-GUI невозможна с Linux-агента без Windows-runner |
| Electron/WebView2 | красиво, но ~100 МБ+ — избыточно для формы заявки |
| PowerShell + WinForms | без сборки, но нет «одного EXE» и хуже поддержка |

## Версионирование и автообновление

- Каждый успешный пуш в ветку проекта запускает CI. Сначала **проверяется код**
  (синтаксис + lint + тесты) — релиз выходит **только после её успешного прохождения**.
  Затем CI **собирает EXE и создаёт GitHub Release с последовательным номером**
  (`v1`, `v2`, … = число релизов + 1).
- Клиент при старте сверяет свой `APP_VERSION` с последним релизом и при необходимости
  заменяет свой EXE (файл лежит в профиле пользователя, поэтому права админа не нужны).
- Подробности и устранение неполадок: [DEPLOYMENT.md](DEPLOYMENT.md), разделы 7–9.

## Безопасность единого логина

Приложение работает от обычного пользователя, поэтому общий пароль Jira технически
читаем на ПК. Обязательно используйте **выделенный сервисный аккаунт Jira только с
правом создавать заявки** (принцип наименьших прав). Подробнее и про «брокер» — в
DEPLOYMENT.md (раздел 8) и AGENTS.md (раздел 7).

## Тестирование логики

```bash
python -m pip install -r requirements.txt pytest
python tests/test_logic.py   # 5+ тестов: конфиг, сбор системы, Jira (mock), версии/обновления
```

> GUI (tkinter) не тестируется на Linux-агенте (нет дисплея/tkinter) — визуальную проверку
> выполняйте на Windows. Вся окружающая логика покрыта тестами.
